Eliminating High-Concurrency MySQL Memory Starvation: When the OS Page Cache Collides with the InnoDB Buffer Pool

By Praveen, Infrastructure Architect | Technical Contributor for Mydbops

The 80% RAM Myth in High-Throughput Environments

For more than a decade, the standard DBA rule of thumb for dedicated database servers has been straightforward: allocate 70% to 80% of total physical RAM to innodb_buffer_pool_size. On a dedicated bare-metal host with predictable point-lookup workloads, this calculation provides reasonable performance while leaving enough headroom for the operating system. However, in high-throughput cloud environments running MySQL 8.0, 8.4 LTS, or 9.0, this rule frequently leads to sudden, unexplained database crashes caused by the Linux Out-Of-Memory (OOM) Killer.

When a database process is killed by signal 9 with no entry in mysql-error.log, administrators often assume hardware failure or an unlogged memory leak. In reality, the crash is almost always the result of a silent collision between MySQL connection overhead, the Linux kernel page cache, and InnoDB's internal buffering.

How Connection Buffers and Kernel Page Caches Starve the Host

The core issue stems from how memory is categorized outside the buffer pool. An enterprise database instance consumes memory across three competing domains:

  • Global Static Buffers: The InnoDB buffer pool, adaptive hash index, and redo log buffer.
  • Thread-Allocated Session Memory: Per-connection allocations including sort_buffer_size, read_buffer_size, join_buffer_size, and max_heap_table_size. Under a traffic surge of 500 active concurrent connections, temporary table allocations can quietly demand an extra 16 GB to 32 GB of heap memory.
  • The Linux VFS Page Cache: During automated logical backups (mysqldump), bulk data loads, or external reporting queries, the Linux Virtual File System caches raw disk blocks in memory. While page cache pages are technically "reclaimable", the kernel cannot free dirty pages synchronously fast enough under severe memory pressure.

When sudden query spikes demand heap memory while the page cache is heavily saturated with unwritten dirty pages, Linux enters synchronous page reclamation mode. Memory allocation latencies spike from microseconds to hundreds of milliseconds. If free memory drops below vm.min_free_kbytes, the Linux kernel invokes oom_kill_process, targeting mysqld as the single process consuming the most RSS memory.

Kernel Tuning: Forcing O_DIRECT and Capping Dirty Pages

To build a production environment resilient against OOM termination, database engineers must configure MySQL and the Linux kernel to respect each other's memory boundaries:

  • Enforce innodb_flush_method = O_DIRECT: This ensures InnoDB reads and writes data files directly to NVMe storage, bypassing the Linux page cache and eliminating double-buffering entirely.
  • Cap Kernel Dirty Page Ratios: Set vm.dirty_background_ratio = 5 and vm.dirty_ratio = 10 in /etc/sysctl.conf. This forces the kernel flusher threads (kworker) to continuously flush dirty pages to storage before they consume free RAM.
  • Conservative Swappiness: Set vm.swappiness = 1 or 10. While some DBAs disable swap entirely (vm.swappiness = 0), this removes the kernel's emergency release valve, converting a brief disk throttle into an immediate mysqld fatal crash.

Conclusion: Reliability Over Raw Allocation

Maximizing database uptime is not about assigning the largest possible percentage of RAM to InnoDB. A database server configured with a 65% buffer pool, O_DIRECT flushing, capped dirty page thresholds, and adequate per-thread connection headroom will consistently outperform a brittle 80% allocation that periodically succumbs to OOM termination. By aligning Linux virtual memory parameters with InnoDB's execution profile, DBAs can ensure predictable throughput without midnight outage alerts.
