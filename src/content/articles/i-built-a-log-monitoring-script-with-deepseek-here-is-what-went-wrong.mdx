## 1. The Problem That Kept Us Up at Night

Every morning, our team found ourselves scrolling through `/var/log/nginx/error.log`, trying to spot new issues. Our servers were generating hundreds of errors overnight, and we needed a way to know when things went south quickly. The pattern was clear: if we saw more than three errors in a 5-minute window, we wanted an alert. 

What we needed was a lightweight [Python script](/blog/automate-weekly-student-grade-reports-with-a-python-script-and-deepseek-prompts) that could:
- Tail the log file in real-time
- Count errors in rolling windows
- Send a ping to my Slack whenever the thresholds were crossed
- Run smoothly on any Ubuntu box without heavy dependencies

After a week of coding manually, I thought, "Why not ask AI for help -  So, I turned to DeepSeek to generate the complete workflow, hoping to learn how to prompt AI for real automation tasks.

Here were some other issues I stumbled upon:

2. The webhook payload had non-serializable datetime objects.
3. OpenCode's version entirely omitted the webhook functionality.
4. Neither version properly handled missing dependencies.

The cost for using DeepSeek was minimal (around $0.0018 for the API call), but the debugging time? That really added up.

## 4. How I Fixed the AI's Code

I took DeepSeek's output as a starting point and made these key improvements:

1. **Dependency checks** - I added clear error messages when `colorama` or `requests` were missing.
2. **Proper windowing** - I fixed the deque logic to maintain error counts across checks.
3. **JSON fixes** - I converted datetimes to ISO strings before the webhook calls.
4. **Graceful degradation** - Made colored output optional if `colorama` isn't available.
5. **Better daemonizing** - Switched to `python-daemon` for proper PID file handling.
6. **Robust logging** - Added log rotation to avoid disk bloat.

The final script runs in 0.32 seconds for initial load and uses minimal CPU (under 2% on a 2-core server).

## 5. Key Lessons Learned

1. **AI is like a junior dev** - Great for first drafts but really needs careful review.
2. **Test in clean environments** - What works on your dev machine might fail elsewhere.
3. **Prompt specifically** - My detailed prompt helped, but I still had to add "check for missing packages."
4. **Log everything** - Proper logging saved me hours of debugging.
5. **Cost vs. quality** - DeepSeek's output was more useful despite the small cost.

The fixed script has been running smoothly on my production servers for a month now. It's not enterprise-grade (you'd likely want to add proper rate limiting and TLS verification for that), but it does solve my immediate problem.

## 7. Advanced CI/CD Integration

To make this script truly production-ready, our team integrated it directly into our GitLab CI/CD pipeline. Instead of running it manually, we deployed it as a systemd service managed by Ansible. 

First, we wrote an Ansible playbook to deploy the script and its dependencies:

```yaml
- name: Deploy Log Monitor
  hosts: webservers
  tasks:
    - name: Install requirements
      pip:
        name: 
          - colorama
          - requests
          - python-daemon
        state: present

    - name: Copy log monitor script
      copy:
        src: files/log_monitor.py
        dest: /usr/local/bin/log_monitor.py
        mode: '0755'

    - name: Set up systemd service
      template:
        src: templates/log-monitor.service.j2
        dest: /etc/systemd/system/log-monitor.service
      notify: restart log-monitor
```bash

Then, we configured the `systemd` unit file to ensure it restarts automatically on failure and starts on boot:

```ini
[Unit]
Description=DeepSeek Log Monitor Service
After=network.target nginx.service

[Service]
Type=simple
User=root
ExecStart=/usr/bin/python3 /usr/local/bin/log_monitor.py --webhook ${SLACK_WEBHOOK_URL}
Restart=always
RestartSec=5
EnvironmentFile=/etc/log-monitor/env

[Install]
WantedBy=multi-user.target
```

This deployment strategy completely removed the human element. The script now starts automatically whenever a server is provisioned or rebooted, pulling its configuration from a secure environment file rather than hardcoded variables. We also set up Prometheus to scrape the error counts directly from the log monitor, giving us a visual dashboard in Grafana alongside the Slack alerts.
