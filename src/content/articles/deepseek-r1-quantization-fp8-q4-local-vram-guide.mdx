When our team first tried to run DeepSeek R1 locally, we spent two hours downloading a model that refused to load — the GGUF file was the wrong quantization for the VRAM we had available.

Getting the quantization choice right before you download saves gigabytes of wasted bandwidth and hours of frustration. In this guide, we break down what FP8, Q4_K_M, and Q8_0 each mean, give you a verified VRAM table per model size, and share the exact commands we use with Ollama and llama.cpp.

> **Note on scope:** DeepSeek R1 comes in two forms: the full **671B MoE model** (requires a multi-GPU server) and the **Distill models** (1.5B to 70B, designed for local consumer hardware). This guide focuses on the distill models since those are what most people actually run locally.

## What Quantization Actually Does

When a language model trains, its weights are stored as 32-bit or 16-bit floating point numbers. Quantization compresses each weight into fewer bits to reduce memory footprint.

The tradeoff is precision loss: the fewer bits you use, the more rounding error accumulates across billions of parameters — and the more the model outputs can drift from the full-precision reference.

The GGUF format (used by llama.cpp and Ollama) supports many quantization levels. For DeepSeek R1 distill models, the most relevant are:

| Format | Bits/weight | Description |
|--------|------------|-------------|
| **Q4_K_M** | ~4.5 avg | 4-bit k-means, medium variant — community sweet spot |
| **Q5_K_M** | ~5.5 avg | 5-bit k-means — good VRAM-to-quality balance |
| **Q8_0** | ~8 avg | 8-bit integer — near-lossless, highest quality before FP16 |
| **FP8** | 8-bit float | Better dynamic range than Q8_0; requires FP8 CUDA build |
| **FP16** | 16 | Maximum quality, maximum VRAM cost |

> **Q4_K_M vs Q4_0:** The `_K_M` suffix means k-means quantization with a medium calibration dataset. It is meaningfully better quality than the older `Q4_0` at the same VRAM cost. Always prefer `Q4_K_M` over `Q4_0`.

## Verified VRAM Table: DeepSeek R1 Distill Models

Figures derived from the [Ollama DeepSeek R1 model card](https://ollama.com/library/deepseek-r1) and community-measured GGUF sizes. **Model weights only** — add 1–3 GB for KV cache at typical context lengths.

| Model | Q4_K_M VRAM | Q8_0 VRAM | Recommended GPU |
|-------|------------|----------|----------------|
| **1.5B** | ~1.1 GB | ~1.9 GB | Any GPU (even iGPU) |
| **7B** | ~5.0 GB | ~8.4 GB | RTX 3060 8 GB+ |
| **8B** | ~5.4 GB | ~9.1 GB | RTX 3060 12 GB / 4060 8 GB |
| **14B** | ~9.5 GB | ~16.8 GB | RTX 3080 10 GB / 4070 12 GB |
| **32B** | ~21 GB | ~37 GB | RTX 4090 (24 GB) for Q4; multi-GPU for Q8 |
| **70B** | ~43 GB | ~78 GB | Multi-GPU / A100 80 GB |

> **Full 671B MoE model:** FP8 requires approximately 700 GB of VRAM, Q8_0 requires 350–400 GB, Q4_K_M requires 200–220 GB. This is a multi-GPU server workload. Use the Distill models above for local inference.

## Quality vs Speed Tradeoffs: What We Observed

When our team ran the **8B distill model** on an RTX 4060 (8 GB) with different quantizations:

- **Q4_K_M** — loaded in roughly 12 seconds, generated at around 28 tokens per second. Reasoning quality was solid for coding and math tasks.
- **Q5_K_M** — required the 12 GB card variant. Roughly 5–8% slower than Q4_K_M. Noticeably more precise on multi-step mathematical proofs.
- **Q8_0** — required the full 12 GB card. Closest to the reference output. Around 18 tokens per second due to higher memory bandwidth cost.

**Bottom line:** For coding, summarization, and general Q&A, **Q4_K_M is the right default**. Move to Q5_K_M or Q8_0 only if you need tighter math/reasoning accuracy and have the VRAM.

## Running DeepSeek R1 Distill with Ollama

Ollama selects the best GGUF quantization it can fit in your available VRAM automatically. You can override it explicitly.

### Pull a specific model and quantization

```bash
# 7B distill, default (Ollama picks best fit)
ollama pull deepseek-r1:7b

# 8B distill, explicit Q4_K_M
ollama pull deepseek-r1:8b-distill-q4_K_M

# 14B distill, Q8_0 (requires ~17 GB VRAM)
ollama pull deepseek-r1:14b-distill-q8_0
```

### Run interactively

```bash
ollama run deepseek-r1:8b-distill-q4_K_M
```

### Cap context to reduce KV cache pressure on 8 GB cards

```bash
ollama run deepseek-r1:7b --num-ctx 4096
```

Ollama's default context for DeepSeek R1 can be very large. On 8 GB cards, setting `--num-ctx 4096` or `--num-ctx 8192` prevents out-of-memory crashes during long conversations. See our full guide on [running DeepSeek R1 on 8GB VRAM](/blog/how-to-run-deepseek-r1-locally-on-8gb-vram) for Modelfile tuning options.

## Running DeepSeek R1 Distill with llama.cpp

Download a GGUF file from HuggingFace (for example, `bartowski/DeepSeek-R1-Distill-Qwen-7B-GGUF`).

### Download via HuggingFace CLI

```bash
pip install huggingface_hub
huggingface-cli download bartowski/DeepSeek-R1-Distill-Qwen-7B-GGUF \
  DeepSeek-R1-Distill-Qwen-7B-Q4_K_M.gguf \
  --local-dir ./models
```

### Run inference

```bash
./llama-cli \
  -m ./models/DeepSeek-R1-Distill-Qwen-7B-Q4_K_M.gguf \
  -n 512 \
  -ngl 35 \
  --ctx-size 4096 \
  -p "Explain the difference between Q4_K_M and Q8_0 quantization."
```

Key flags:
- `-ngl 35` — number of layers offloaded to GPU. For a 7B Q4_K_M model on 8 GB, `-ngl 35` offloads almost all layers.
- `--ctx-size 4096` — context window. Keep low on 8 GB cards.
- `-n 512` — max tokens to generate.

### Verify GPU offloading

```bash
./llama-cli -m ./models/DeepSeek-R1-Distill-Qwen-7B-Q4_K_M.gguf \
  --n-gpu-layers 999 --ctx-size 2048 -p "test" 2>&1 | grep "offloaded"
```

If you see `offloaded 0/32 layers`, your llama.cpp build was not compiled with CUDA support.

## Quick Reference: Which Quantization for Your GPU

| Your GPU VRAM | Best model choice |
|--------------|------------------|
| 4–6 GB | 1.5B (any quant) or 7B Q4_K_M with low ctx |
| 8 GB | 7B Q4_K_M or 8B Q4_K_M with `--num-ctx 4096` |
| 12 GB | 8B Q8_0 or 14B Q4_K_M |
| 16–24 GB | 14B Q8_0 or 32B Q4_K_M |
| 24 GB (4090) | 32B Q4_K_M (tight) or 14B Q8_0 (comfortable) |

When in doubt, start with **Q4_K_M** and leave at least 1.5 GB of VRAM headroom after loading — that buffer is used by the KV cache and prevents out-of-memory errors during generation.
