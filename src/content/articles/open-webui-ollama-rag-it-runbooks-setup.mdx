During a network outage or server crash, searching through dozens of internal Confluence pages, PDF network diagrams, and scattered text runbooks wastes critical minutes. In our team's experience, this fragmented knowledge retrieval is the primary bottleneck for incident response.

While public AI tools like ChatGPT or Claude can summarize documents, **uploading proprietary IP addresses, network topologies, or database passwords to public cloud APIs violates IT compliance policies.**

On our IT operations workbench, we built a 100% offline solution: **Open WebUI combined with local Ollama embeddings (`nomic-embed-text`) running Retrieval-Augmented Generation (RAG).**

Here is our step-by-step setup guide, hardware requirements, and chunking parameters for indexing technical documentation privately.

---
## 🛠️ The Local RAG Architecture

```bash
[Local Markdown / PDF Runbooks]
             │
             ▼
[Open WebUI Document Ingestion Engine]
             │
             ▼ (Chunking: 512 tokens / Overlap: 50)
[Ollama nomic-embed-text Model (Vector Embedding)]
             │
             ▼
[Local Chromadb Vector Store]
             │
             ▼ (Query Retrieval)
[DeepSeek R1 / Llama 3.1 Local Model Response]
```bash

---
## Step 1: Install Ollama & Required Models

First, pull both your primary chat model and the dedicated embedding model into Ollama:

```bash
## Pull chat model
ollama pull deepseek-r1:8b
```

## Pull dedicated vector embedding model
ollama pull nomic-embed-text

`nomic-embed-text` is specifically trained for technical semantic retrieval with an 8,192 token context window, outperforming generic OpenAI text-embedding-ada-002 models on code and configuration files.

---
## Step 2: Configure Open WebUI via Docker

Launch Open WebUI using Docker Desktop or Podman on your workstation:

```bash
docker run -d -p 3000:8080 \
  --add-host=host.docker.internal:host-gateway \
  -v open-webui:/app/backend/data \
  --name open-webui \
  --restart always \
  ghcr.io/open-webui/open-webui:main
```

Open your browser to `http://localhost:3000` and create your local admin account.

---
## Step 3: Configure Optimal Document RAG Parameters

In Open WebUI, navigate to **Admin Panel > Settings > Documents**:

1. **Embedding Model Engine:** Select `Ollama`.
2. **Embedding Model:** Select `nomic-embed-text:latest`.
3. **Chunk Size:** Set to `512` (Optimal for technical documentation with code blocks).
4. **Chunk Overlap:** Set to `64` (Prevents cutting off PowerShell functions across chunk boundaries).
5. **Top K Retrieval:** Set to `4` (Fetches the 4 most relevant text snippets per query).

---
## Step 4: Ingesting Runbooks & Querying Privately

1. Click the **Workspace > Knowledge** tab.
2. Create a new Knowledge Base named `IT-Infrastructure-Runbooks`.
3. Drag and drop your `.md`, `.txt`, `.pdf`, or `.docx` incident runbooks into the upload dropzone.
4. Open a new chat session, type `#IT-Infrastructure-Runbooks`, and ask:
   *"What is the failover procedure if the primary Active Directory domain controller loses sync?"*

Open WebUI will retrieve the exact lines from your local documents, display source citations, and generate plain-English remediation steps without a single byte leaving your local network.

## Advanced Maintenance: Updating the Vector Store and Network Security

On our team's IT workbench, simply standing up the RAG system wasn't the final step. We had to ensure the vector database stayed synchronized with our live documentation and that the endpoint was secured against unauthorized queries from junior staff.

### Automating Document Syncs

When a senior engineer updates a disaster recovery runbook on Confluence, the local Open WebUI instance does not magically know about it. Vector stores rely on point-in-time document embeddings.

To solve this, we implemented a scheduled Python script using the Open WebUI REST API. Every night at 2:00 AM, the script pulls the latest exported PDFs from our documentation repository, compares file hashes, and uses the `/api/v1/documents/` endpoint to re-chunk and embed the updated files into the ChromaDB instance. This ensures that when the system asks for the IP address of the primary database server, it retrieves the address configured yesterday, not the one from six months ago.

### Hardware Considerations for Production RAG

While you can technically run this pipeline on a laptop CPU, doing so under pressure during a sev-1 outage is agonizing. The `nomic-embed-text` embedding process is CPU-bound if not offloaded, but the retrieval and generation phases (powered by Llama 3 or DeepSeek) absolutely require a dedicated GPU.

For a team of 10 system administrators querying the tool concurrently, we recommend provisioning an Ubuntu server equipped with at least an NVIDIA RTX 4070 (12GB VRAM) or an older Tesla T4. This guarantees that token generation remains above 30 tokens per second, allowing engineers to get immediate answers rather than waiting 45 seconds for a single paragraph.

### Securing the Open WebUI Endpoint

Because this RAG instance contains the literal blueprints to your entire network architecture, it cannot sit exposed on the local LAN without authentication. By default, Open WebUI allows the first user to register as an administrator. 

We highly recommend deploying the Docker container behind an NGINX reverse proxy with TLS encryption, and integrating Open WebUI's built-in OAuth support with your Azure AD or Okta tenant. This enforces Multi-Factor Authentication (MFA) before any engineer can ask the AI for administrative runbooks, fulfilling zero-trust security architecture requirements.
