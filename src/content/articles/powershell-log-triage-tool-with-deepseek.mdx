Our team found that reading raw Windows Event Viewer logs during a production outage is painful. Between cryptically formatted `EventID` numbers, raw XML strings, and thousands of benign `Information` logs, finding the single failing driver or authentication leak takes precious time.

On our IT operations workbench, we set out to solve this: **Can we build a lightweight PowerShell script that automatically extracts system errors, sends them to a local DeepSeek model via Ollama API, and returns plain-English root cause analysis?**

Here is the exact script we built, the prompt engineering required, and the two major bugs we had to fix when DeepSeek hallucinates Windows cmdlets.

---
## 🛠️ The Architecture

```
[Windows Event Log (Get-WinEvent)] 
        │
        ▼ (Filter Error/Warning IDs)
[PowerShell Sanitizer Script]
        │
        ▼ (JSON Payload)
[Local Ollama DeepSeek R1 API (http://localhost:11434)]
        │
        ▼
[Markdown Incident Report + Action Plan]
```

## The Working PowerShell Script

```powershell
## Get-EventLogTriage.ps1
param (
    [int]$HoursAgo = 2,
    [string]$LogName = "System"
)

$StartTime = (Get-Date).AddHours(-$HoursAgo)

Write-Host "Extracting Critical & Error events from $LogName since $StartTime..." -ForegroundColor Cipher

$Events = Get-WinEvent -FilterHashtable @{
    LogName = $LogName
    Level = 1,2 # 1=Critical, 2=Error
    StartTime = $StartTime
} -ErrorAction SilentlyContinue | Select-Object -First 15 TimeCreated, Id, ProviderName, Message

if (-not $Events) {
    Write-Host "No critical or error events found in the last $HoursAgo hours!" -ForegroundColor Green
    exit
}

$LogText = $Events | Format-Table -AutoSize | Out-String

$Prompt = @"
You are an expert Windows Systems Administrator.
Analyze the following raw Windows Event Log entries and provide:
1. Root Cause Summary (1-2 sentences)
2. Affected Components
3. Recommended PowerShell Remediation Commands

LOG DATA:
$LogText
"@

$Body = @{
    model = "deepseek-r1:8b"
    prompt = $Prompt
    stream = $false
} | ConvertTo-Json

Write-Host "Sending logs to DeepSeek R1..." -ForegroundColor Yellow

$Response = Invoke-RestMethod -Uri "http://localhost:11434/api/generate" -Method Post -Body $Body -ContentType "application/json"

Write-Host "`n=== DEEPSEEK TRIAGE REPORT ===" -ForegroundColor Cyan
Write-Host $Response.response
```

## Where the Script Failed (And How We Fixed It)

### Failure 1: DeepSeek Hallucinated Non-Existent Cmdlets
When analyzing an `nvlddmkm` GPU driver crash, DeepSeek recommended running `Reset-NvidiaDriver`. That cmdlet does not exist in PowerShell!

**Fix:** Added strict system prompt constraints: *"Only recommend official Microsoft PowerShell cmdlets (e.g., Get-Service, Restart-Service, DISM, sfc). Never invent custom cmdlets."*

### Failure 2: Token Limit Overflow
Sending 500 raw log entries exceeded Ollama's default context window, causing silent truncation.

**Fix:** Added `-First 15` limit on `Get-WinEvent` and stripped verbose message headers before sending the payload.

## Advanced Upgrades: Scheduling and Scale

While running this script manually during an active incident is helpful, our team found the most value when we automated the triage process completely. 

### Automating via Windows Task Scheduler

To proactively catch failing services before end-users report them, you can bind this PowerShell script to Windows Task Scheduler. Configure the trigger to run every 4 hours. 

Instead of writing the output to the console (`Write-Host`), you can modify the script to dump the DeepSeek markdown report into a shared IT department Slack or Microsoft Teams webhook. This way, when the sysadmin team logs in on Monday morning, they already have an AI-generated summary of any disk failures, unexpected reboots, or authentication brute-force attempts that occurred over the weekend.

### Expanding to Multiple Remote Servers

The basic script targets the local `localhost` machine. However, `Get-WinEvent` natively supports the `-ComputerName` parameter. By wrapping the core logic in a `foreach` loop and providing an array of your domain controllers or critical SQL servers, a single local Ollama node can triage logs across your entire infrastructure fleet simultaneously.

```powershell
$Servers = @("DC01", "SQL-PROD-01", "FILE-SHARE-02")
foreach ($Server in $Servers) {
    # Run Get-WinEvent remotely, send payload to local DeepSeek API
}
```

### Security and Privacy Benefits of Local AI Triage

The primary reason we engineered this solution using Ollama and DeepSeek rather than relying on OpenAI's API is strict data privacy. Windows Event Logs frequently contain Sensitive Personal Information (SPII), including Active Directory usernames, internal IP topologies, machine names, and sometimes even plaintext passwords leaked by poorly coded legacy applications. 

By keeping the inference engine 100% on-premises, your organization remains completely compliant with GDPR, HIPAA, and internal zero-trust network mandates. No log data ever crosses the firewall perimeter.

### Alternative AI Models to Try (Llama 3 vs DeepSeek)

While our script defaults to `deepseek-r1:8b` because of its outstanding reasoning capabilities and small VRAM footprint, you can easily swap the Ollama API model parameter depending on your available hardware. 

If you are running this on a beefy Sysadmin workstation with 24GB of VRAM (like an RTX 4090 or RTX 3090), you might consider changing the `$Body.model` payload to `llama3:70b`. The larger parameter count of Llama 3 often provides better natural language formatting and more robust PowerShell syntax correction when generating remediation scripts. Conversely, if you are running this triage tool on a constrained 1U rack server without a dedicated GPU, you can swap the model to `phi3:mini`, which runs incredibly fast on CPU-only infrastructure while still identifying critical event log anomalies.
