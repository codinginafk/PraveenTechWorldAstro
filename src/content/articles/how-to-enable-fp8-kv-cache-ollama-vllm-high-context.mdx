If you have tried feeding large codebases, technical manuals, or lengthy legal contracts (60,000+ tokens) into local open-weights models like **Qwen 2.5 14B** or **DeepSeek R1 Distill 14B**, you have almost certainly encountered this frustrating barrier:

```text
torch.OutOfMemoryError: CUDA out of memory. 
Tried to allocate 2.45 GiB (GPU 0; 23.69 GiB total capacity; 22.14 GiB already allocated)
```

Developers often assume the model itself is too big for their GPU. But when you inspect VRAM allocation, a 4-bit quantized 14B model (`Q4_K_M`) only takes **~8.5 GB** of memory.

Where did the remaining 15.5 GB disappear? **The unquantized Key-Value (KV) cache.**

On our AI engineering workbench, we benchmarked FP8 KV caching across vLLM and Ollama. Here is the exact memory math, how FP8 cuts cache memory by 50%, and the configuration flags to run 128K context locally on consumer GPUs.

---

## 🧮 The KV Cache Memory Formula: Why Context Explodes

In Transformer architectures, attention matrices must retain key and value vectors for every historical token to avoid recalculating past context.

The exact memory required for the KV cache is calculated as:

```text
Memory per Token = 2 * Layers * KV_Heads * Head_Dimension * Precision_Bytes
```

Where:
- **Layers**: Number of Transformer layers (e.g., 48)
- **KV_Heads**: Number of Key/Value attention heads (e.g., 8)
- **Head_Dimension**: Dimension of each attention head (e.g., 128)
- **Precision_Bytes**: Bytes per precision element (2 for FP16, 1 for FP8)

### Comparing Memory for a 14B Model (48 Layers, 8 KV Heads, Dim 128):

```
┌────────────────────────────────────────────────────────┐
│  KV Cache VRAM Footprint vs. Context Length (14B Model)│
├────────────────────────────────────────────────────────┤
│                                                        │
│  Context Length   FP16 (Standard)     FP8 (Quantized)  │
│  ──────────────   ───────────────     ───────────────  │
│   8,192 tokens       1.57 GB             0.79 GB       │
│  32,768 tokens       6.29 GB             3.14 GB       │
│  65,536 tokens      12.58 GB             6.29 GB       │
│ 131,072 tokens      25.16 GB ❌ OOM     12.58 GB ✅ OK  │
│                                                        │
└────────────────────────────────────────────────────────┘
```

At FP16, a 128K context window demands **25.16 GB** solely for the cache. On a 24GB card (RTX 3090/4090/5070 Ti), the session crashes long before hitting full capacity.

With **FP8 quantization**, that same 128K cache drops to **12.58 GB**. Adding 8.5 GB of model weights results in **21.08 GB total VRAM**, fitting comfortably with room for CUDA runtime buffers!

## 🛠️ Step 1: Enabling FP8 KV Cache in vLLM

vLLM provides native hardware-accelerated FP8 attention kernels on NVIDIA Ada Lovelace (RTX 40-series), Hopper, and Blackwell architectures.

Launch the vLLM server with FP8 cache enabled:

```bash
# Launch vLLM server with FP8 KV cache and 128k context
python3 -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-14B-Instruct-GPTQ-Int4 \
  --kv-cache-dtype fp8 \
  --max-model-len 131072 \
  --gpu-memory-utilization 0.95 \
  --trust-remote-code
```

- `--kv-cache-dtype fp8`: Activates 8-bit dynamic quantization on key-value tensors.
- `--gpu-memory-utilization 0.95`: Allocates remaining VRAM as contiguous PagedAttention blocks.

## 🛠️ Step 2: Enabling Flash Attention in Ollama & llama.cpp

In Ollama, unquantized context expansion often triggers CPU fallback loops. To optimize memory layout and enable Flash Attention:

1. Create a custom `Modelfile` with Flash Attention and context parameters:

```dockerfile
FROM deepseek-r1:14b

# Set 128k context window
PARAMETER num_ctx 131072

# Enable Flash Attention for memory optimization
PARAMETER flash_attn true
```

2. Launch Ollama with Flash Attention environment flags:

```bash
# Enable hardware flash attention in Ollama
export OLLAMA_FLASH_ATTENTION=1
ollama run deepseek-r1:14b-custom
```
