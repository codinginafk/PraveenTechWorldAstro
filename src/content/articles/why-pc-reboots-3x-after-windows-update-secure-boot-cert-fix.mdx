If you turned on your computer recently, watched Windows Update hit 30%, restart, spin at 75%, restart again, and finally display **"Something didn't go as planned. No need to worry—undoing changes"** before restarting a third time, you are not alone.

On our IT operations workbench, we saw a sudden wave of Windows 11 workstations entering this exact **3-reboot rollback loop**.

The underlying cause behind this recent wave is not corrupt disk sectors or third-party antivirus software. It is the mandatory **Microsoft UEFI Secure Boot Forbidden Signature Database (DBX) certificate rotation wave**, which causes the Windows Servicing Stack to throw error **`0x800f0983`** (`CBS_E_IMAGE_CERT_REVOKED`).

Here is what happens during those three reboots, how to verify the error in your `CBS.log`, and how our team resolves the rollback loop permanently.

---

## 🔄 What Actually Happens During the 3-Reboot Rollback Sequence

When a Windows cumulative update modifies low-level kernel drivers or UEFI boot managers (`bootmgfw.efi`), Windows cannot apply the changes while the operating system is actively running. It stages the files and schedules a multi-stage offline execution.

```
┌────────────────────────────────────────────────────────┐
│  The 3-Reboot Rollback Lifecycle                       │
├────────────────────────────────────────────────────────┤
│                                                        │
│  [Reboot 1: Staging Phase (30% Progress)]              │
│  - Windows shuts down kernel and writes new boot files │
│  - Reboots into Windows Recovery Environment (WinRE)   │
│                          │                             │
│                          ▼                             │
│  [Reboot 2: UEFI Verification Phase (75% Progress)]   │
│  - UEFI Firmware verifies bootmgfw.efi against DBX     │
│  - Signature mismatch detected ➔ Error 0x800f0983       │
│                          │                             │
│                          ▼                             │
│  [Reboot 3: Automated Rollback Phase]                  │
│  - Windows uninstalls staged packages                  │
│  - Restores previous working BCD & boots to Desktop   │
│                                                        │
└────────────────────────────────────────────────────────┘
```

1. **Reboot 1 (Staging Execution):** Windows closes user sessions, enters the servicing environment, and replaces staged operating system binaries in `C:\Windows\System32`.
2. **Reboot 2 (UEFI Signature Handshake):** The motherboard UEFI firmware reads the updated boot manager in the EFI System Partition (`\EFI\Microsoft\Boot\bootmgfw.efi`). If the motherboard NVRAM has an out-of-sync DBX revocation table, the signature validation fails with error `0x800f0983`.
3. **Reboot 3 (Safety Rollback):** The Windows Servicing Stack detects the verification failure, aborts installation, restores the previous known-good registry hives and boot loader, and restarts back into the normal desktop.

## 🔍 Step 1: Verify Error 0x800f0983 in the CBS Log

To confirm whether your 3-reboot rollback is caused by the Secure Boot certificate rotation, inspect the Component-Based Servicing log:

1. Press `Win + E` to open File Explorer.
2. Navigate to `C:\Windows\Logs\CBS\`.
3. Open `CBS.log` in Notepad (or copy it to your desktop if permissions block direct opening).
4. Press `Ctrl + F` and search for `0x800f0983` or `Fail to stage boot manager`.

```text
2026-08-17 07:15:22, Error CBS Failed to stage execution package [HRESULT = 0x800f0983 - CBS_E_IMAGE_CERT_REVOKED]
2026-08-17 07:15:22, Info  CBS Execution rollback initiated for package: Package_for_RollupFix
2026-08-17 07:15:24, Info  CBS Servicing stack requested reboot to complete rollback
```

If you see `0x800f0983` or `CBS_E_IMAGE_CERT_REVOKED`, follow the steps below to synchronize your UEFI Secure Boot variables.

---

## 🛠️ Step 2: Check Secure Boot State via PowerShell

Open **PowerShell as Administrator** and check your current Secure Boot configuration:

```powershell
# Check if Secure Boot is enabled and active in UEFI
Confirm-SecureBootUEFI
```

- If PowerShell outputs `True`: Secure Boot is actively enforcing certificate validation.
- If PowerShell outputs `False`: Secure Boot is disabled in BIOS, and the rollback is likely caused by an EFI System Partition size bottleneck (see Step 4).

Next, check your motherboard firmware environment:

```powershell
Get-SecureBootUEFI -Name "dbx" | Select-Object -ExpandProperty Bytes | Measure-Object -Sum
```

If your motherboard has not received a BIOS update in over 18 months, its internal DBX database is missing updated revocation keys, causing modern cumulative security patches to fail verification.

---

## 🛠️ Step 3: Apply the Microsoft DBX Update & Reset Servicing Stack

To resolve the certificate mismatch, manually reset the Windows Update cache and apply the update with administrative privileges.

### 1. Stop Windows Update Services
Run the following commands in an elevated PowerShell terminal:

```powershell
# Stop servicing services
Stop-Service -Name wuauserv -Force
Stop-Service -Name cryptSvc -Force
Stop-Service -Name bits -Force
Stop-Service -Name msiserver -Force

# Rename corrupted cache folders
Rename-Item -Path "C:\Windows\SoftwareDistribution" -NewName "SoftwareDistribution.old" -Force
Rename-Item -Path "C:\Windows\System32\catroot2" -NewName "catroot2.old" -Force

# Restart services
Start-Service -Name wuauserv
Start-Service -Name cryptSvc
Start-Service -Name bits
Start-Service -Name msiserver
```

## 🛠️ Step 4: Verify EFI System Partition (ESP) Free Space

A common secondary trigger for 3-reboot rollbacks during bootloader updates is a full **EFI System Partition (ESP)**. When Windows Update attempts to stage updated bootloader files, a 100MB ESP with less than 15MB of free space will fail silently.

1. Open PowerShell as Administrator.
2. Mount the hidden EFI System Partition to drive letter `S:`:

```powershell
# Mount EFI partition
mountvol S: /s

# Check available disk space
Get-Volume -DriveLetter S
```

If free space on drive `S:` is under 15MB:
- Check `S:\EFI\Microsoft\Boot\Fonts\` and remove unnecessary language font files (retain `chs_boot.ttf`, `wgl4_boot.ttf`, and standard defaults).
- Once cleaned, unmount the EFI drive:

```powershell
mountvol S: /d
```

---

## 🛠️ Step 5: Repair Component Store with DISM and SFC

Run the Windows repair engine to ensure system binaries and certificate catalogs match the baseline:

```powershell
# 1. Restore servicing health from clean Windows component store
dism.exe /Online /Cleanup-Image /RestoreHealth

# 2. Re-verify protected system files
sfc /scannow
```

Restart your PC once `sfc` finishes. Then navigate to **Settings > Windows Update** and click **Check for updates**. The cumulative update will now stage cleanly and complete on the first reboot.
